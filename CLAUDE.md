## What This Project Does

Swift Explorer is a macOS desktop app that lets users paste Swift code and see the resulting LLVM IR and assembly output, similar to Compiler Explorer. It uses `swiftc -emit-ir` and `swiftc -S` under the hood.

## Commands

**Project generation (Tuist, version pinned in `mise.toml`):**
```bash
# Install the pinned Tuist version
mise install

# Regenerate SwiftExplorer.xcodeproj / .xcworkspace from Tuist.swift + Project.swift
mise exec -- tuist generate --no-open
```
`Tuist.swift` and `Project.swift` are the source of truth for the Xcode project — the generated `.xcodeproj`/`.xcworkspace` are gitignored build artifacts. Run `tuist generate` after pulling changes to either manifest, or after adding/removing source files.

**Build & Test (Xcode 26.2.0 required — see `.xcode-version`):**
```bash
# Run all tests
xcodebuild clean test -workspace SwiftExplorer.xcworkspace -scheme SwiftExplorer -skipPackagePluginValidation

# Run tests for a specific SPM package
xcodebuild test -workspace SwiftExplorer.xcworkspace -scheme SwiftExplorer -only-testing:SwiftExplorerTests/HomeViewModelTests
```

**Lint:**
```bash
swiftlint
```

**Localization strings (requires mise):**
```bash
mise run swiftgen
```

## Architecture

The Xcode project is generated by Tuist from `Tuist.swift` (project config) and `Project.swift` (targets, dependencies, build settings) at the repo root — do not hand-edit `SwiftExplorer.xcodeproj`, it's regenerated by `tuist generate` and is gitignored.

The project uses MVVM with a local module monorepo under `Dependencies/`. Most modules are Swift Package Manager packages; `Common` and `DesignSystem` have been migrated to native Tuist projects (own `Project.swift`) as part of moving modules off SPM. External SPM dependencies for native Tuist modules (e.g. `DesignSystem`'s `CodeEditor` fork) are declared in `Tuist/Package.swift` and referenced via `.external(name:)`; run `mise exec -- tuist install` after changing it. The main Xcode project depends on these modules:

- **Lowlevel** — Core logic. `Llvm.swift` runs `swiftc -emit-ir`, `Assembly.swift` runs `swiftc -S`. `OptimizationLevel` enum maps to compiler flags (`-O`, `-Onone`, `-Osize`, `-Ounchecked`). (SPM package)
- **Analytics** — Firebase Analytics + Crashlytics wrappers. All event names live in `Events.swift` as nested enums (`AnalyticsEvents.Home`, `CrashlyticsEvents.Home`). (SPM package)
- **DesignSystem** — `CustomCodeEditorView` (wraps a CodeEditor fork with Swift/Bash syntax highlighting), `ButtonSelect`, color/font theme extensions. Native Tuist project (own `Project.swift`), consumed via `.project(target:path:)`, not SPM. Fonts are code-generated by a SwiftGen pre-build script (`swiftgen.yml`) into `Sources/DesignSystem/Generated/FontsFamily.swift`, which is checked in.
- **Common** — `AppLinks`, `Bundle+AppVersion`. Native Tuist project (own `Project.swift`), consumed via `.project(target:path:)`, not SPM.
- **CommonTest** — `TestBase`, SwiftUI test helpers shared across package tests. (SPM package)

**Main app layer** (`SwiftExplorer/`):
- `HomeView` — Three code editors (Swift input, LLVM IR output, Assembly output) plus an optimization-level picker and an Explore button.
- `HomeViewModel` — `@Observable` class, holds the three code strings and optimization level. `generate()` calls `Lowlevel` to produce IR and assembly. Accepts `AnalyticsTracking` and `CrashlyticsTracking` via protocol injection.
- `AboutView` — Static about screen.

## Testing Patterns

- ViewModels are tested in `SwiftExplorerTests/` using stub implementations of the Analytics/Crashlytics protocols (e.g., `AnalyticsTrackingStub`).
- Snapshot tests live in `SwiftExplorerTests/__Snapshots__/` — update them intentionally when UI changes.
- Each SPM package has its own `Tests/` target tested through the main scheme.
- `Common` and `DesignSystem` (native Tuist projects) have their own generated schemes instead: run `mise exec -- tuist test Common` / `mise exec -- tuist test DesignSystem`, or `xcodebuild test -workspace SwiftExplorer.xcworkspace -scheme <Module>`.

## Code Conventions

- SwiftLint is enforced; key custom rule: all classes must be `final`.
- Localizable strings are code-generated via SwiftGen into `L10n.swift` — add new strings to the `.strings` file and regenerate, never hardcode UI text.
- Firebase is initialized in `SwiftExplorerApp.swift` on launch; the Analytics module is the only place Firebase is imported.
